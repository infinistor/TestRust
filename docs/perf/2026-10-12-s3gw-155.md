### 해석

1. **스레드 32까지의 Put은 서버의 요청당 처리 시간에 묶여 있다.** 1M Put의 평균 지연은 스레드 16과 32에서 두 도구 모두 약 30ms로 같고, 처리량은 스레드 수에 비례한다(520 → 약 1000 ops/s). 서버가 아직 포화되지 않은 상태에서 요청 하나가 서버에서 약 30ms 걸리므로 처리량은 "스레드 ÷ 30ms"로 정해진다. 클라이언트 CPU 차이(요청당 .NET 4.5~4.8ms, Rust 2.6~2.8ms)는 이 30ms에 비해 작아서 처리량 차이로 거의 나타나지 않는다. 본 측정의 96%는 이 범위 안의 회차 간 편차다(회차별 89·95·103%).
2. **부하를 올리면 .NET이 먼저 한계에 닿는다.** 스레드 64에서 .NET Put은 1238 ops/s에 머물고 지연이 51ms로 늘었지만, Rust는 1555 ops/s(125%), 지연 41ms다. 같은 서버에서 Rust가 더 많이 처리했으므로 .NET의 1238은 서버 한계가 아니라 .NET 클라이언트 쪽 한계다.
3. **작은 파일에서도 Put 차이는 작다.** 4K·64K Put은 두 도구 모두 지연 약 12~13ms로 같고 처리량 비율은 103~105%다. 파일이 작아지면 전송량은 줄지만 객체 하나를 만드는 서버 쪽 고정 비용(메타데이터 기록 등)이 남아 지연을 정한다. 요청당 CPU는 Rust가 59%로 여전히 적다.
4. **Get은 서버가 빨라 클라이언트 효율이 그대로 드러난다.** 1M Get(스레드 16·32)의 Rust 지연은 10~12ms인데 .NET은 19~29ms이고, .NET은 요청당 CPU를 9~13ms 쓴다. 작은 파일에서는 응답 본문 처리 비용이 줄어 차이가 140~158%로 줄어든다.
5. **Mix는 읽기·쓰기가 반씩이라 Get 쪽 이득이 섞여 나온다.** Put이 비슷한 조건에서는 Get 비율이 클수록 Mix 비율도 크다(1M 112~131%, 64K·4K 102~105%).

### Rust Put의 메모리가 더 많은 이유

- Rust는 청크 인코딩을 쓰지 않는 Put에서 본문 전체의 SHA-256을 서명에 넣기 위해(.NET과 같은 요청) 파일을 요청마다 메모리로 통째로 읽는다(`PutBody::into_stream`). 그래서 메모리가 동시에 처리 중인 요청 수 × 파일 크기에 따라 늘어난다: 1M에서 스레드 16·32·64일 때 95·193·525 MiB.
- .NET은 파일을 스트림으로 읽어 보내므로 요청 수·파일 크기와 거의 상관없이 약 140 MiB(런타임 기본 사용량)에 머문다.
- 작은 파일(4K·64K)이나 스레드 16에서는 Rust가 .NET보다 메모리를 적게 쓴다(65·91·95 MiB, .NET 약 142~145 MiB).
- 이 장비는 코어가 384개라 tokio 작업 스레드도 384개이고, mimalloc이 스레드별로 메모리를 잡아 두는 것도 더해졌을 것으로 본다(따로 재지는 않았다).
- 개선 방향: 같은 파일을 반복해 올리므로 파일을 한 번만 읽어 요청끼리 공유하면(요청 헤더는 그대로) 메모리와 읽기 비용을 줄일 수 있다. 이번에는 바꾸지 않았다.
