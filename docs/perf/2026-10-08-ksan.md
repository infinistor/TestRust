## 분석

### Get (Rust 1.57배)

측정 구간과 요청은 같다. .NET `Utility.GetBodySplit`은 본문을 용량 없는 `MemoryStream`에 복사해 1MiB마다 버퍼 재할당·LOH GC가 생긴다(RSS 최대 589MiB). 런타임 처리 비용 차이이며 원본 동작이라 그대로 둔다.

### Put (Rust 0.92, 세 회차 모두 5~11% 낮음)

결론: 클라이언트 성능 차이로 볼 근거가 없다. 같은 버킷에서 짧게 번갈아 재면 KSAN 쪽 회차 편차(±10% 이상) 안에서 같다. 본 측정에서 Rust가 계속 낮은 것은 도구별 버킷(`-perf-net`·`-perf-rs`)과 시간대 편차가 겹친 결과로 본다.

#### 요청 캡처(스레드 1, 3초, 클라이언트↔haproxy 구간)

| | 요청 수 | PUT→200 | 200→다음 PUT(클라이언트 시간) |
| --- | --- | --- | --- |
| .NET | 197 | 13.71 ms(PUT→100 Continue 0.37 ms 포함) | 1.79 ms |
| Rust | 191 | 13.51 ms | 2.18 ms |

- 요청 헤더 차이는 이미 알려진 SDK 차이뿐이다([s3-client.md](../design/s3-client.md)의 "비교하지 않는 차이"). .NET만 `Expect: 100-continue`를 보내지만 서버 처리 시간은 같다.
- SDK 기본 HTTP 클라이언트는 TCP_NODELAY가 켜져 있다(`aws-smithy-http-client` 기본값 `true`). Nagle 지연은 원인이 아니다.

#### CPU 프로파일(20초 Put, 스레드 32)

| | 쓰기 건수(20초) | task-clock | user / sys | context switch |

| | 쓰기 건수(20초) | task-clock | user / sys | context switch |
| --- | --- | --- | --- | --- |
| .NET | 9,401 | 59.5 s | 33.8 / 25.9 s | 547K |
| Rust(mallocng, 배포 빌드) | 8,257 | 50.9 s | 17.0 / 34.8 s | 1,039K |
| Rust(mimalloc, 시험 빌드) | 8,372 | 25.9 s | 16.5 / 10.6 s | 382K |

- mallocng 빌드의 sys 시간은 musl 할당기의 전역 락 경합(`futex_wake ← __unlock`, `__libc_malloc_impl`)과 1MiB 블록의 mmap/munmap(페이지 폴트, TLB IPI)이다. 그래도 총 CPU는 .NET보다 적다.
- mimalloc으로 바꾸면 CPU는 절반이 되지만 처리량은 같다(CPU는 병목이 아니다). 대신 Prepare 최대 RSS가 62MiB에서 822MiB로 늘었다(스레드별 힙이 큰 블록을 쥔다). 이득이 없어 배포 빌드는 musl 기본 할당기로 둔다. (이후 물리 장비 측정에서 musl 할당기가 Put 처리량을 깎는 것이 확인되어, `v1.0.1`부터 메모리 반환 옵션을 준 mimalloc을 쓴다. [2026-10-08-s3gw-155.md](2026-10-08-s3gw-155.md))
